# Portuguese Fiscal Integration & Technical Receipts (Phase 8)

## 1. Portuguese NIF Validation Algorithm

The system implements the official Portuguese Tax Identification Number (NIF - Número de Identificação Fiscal) Modulo-11 verification algorithm (`server/src/services/fiscal/nifValidator.ts`).

### Rules:
1. **Length**: Exactly 9 numeric digits.
2. **Valid First Digit / Prefixes**:
   - `1`, `2`, `3`: Individual persons (Singular)
   - `5`: Legal entities / corporations (Coletiva)
   - `6`: Public entities
   - `8`: Non-resident individuals
   - `9`: Irregular entities or provisional numbers
   - Valid 2-digit prefixes: `45`, `70`, `71`, `72`, `77`, `78`, `79`.
3. **Modulo 11 Checksum**:
   - Digits 1 through 8 are multiplied by weights `9, 8, 7, 6, 5, 4, 3, 2`.
   - `sum = sum(digit[i] * weight[i])`.
   - `remainder = sum % 11`.
   - Expected check digit:
     - If `remainder <= 1`, check digit is `0`.
     - Otherwise, check digit is `11 - remainder`.
   - Expected check digit must match the 9th digit.
4. **Final Consumer (Consumidor Final)**:
   - `999999990` is recognized as the standard Portuguese anonymous consumer identifier.
5. **Foreign / Non-PT Tax Identifiers**:
   - Accepted with a foreign country code (e.g. `ES`, `FR`, `DE`, `GB`, `US`, `OTHER`) and basic alphanumeric character check.

## 2. Technical Receipts vs Certified Legal Invoicing

> [!IMPORTANT]
> **Legal Integration Boundary**:
> Portuguese law requires fiscal invoices submitted for tax clearance to be generated by software certified by the Autoridade Tributária e Aduaneira (AT) under Portaria n.º 31/2019 and Portaria n.º 195/2020.
> 
> AURA Studio produces **Technical Receipts / Internal Conference Documents** (`FiscalDocumentType.RECEIPT`) for dining orders, operational staff cash register balancing, and customer order verification.
> 
> A clean provider abstraction (`FiscalProvider`) is established so that production deployments can plug in an AT-certified provider (e.g., Moloni, Jasmin, PHC, or direct AT Web Services with digital certificates) with zero modifications to application logic.

## 3. Sequential Series Numbering & Immutability

1. **Document Numbering**:
   - Format: `{SERIES_PREFIX}-{YEAR}-{SEQUENCE}` (e.g., `REC-2026-00001`).
   - Sequences are monotonically incremented and scoped to each restaurant series.
   - Enforced by atomic database locking to prevent sequence skips or duplicates.
2. **Immutable Snapshot**:
   - When a receipt is issued, a frozen snapshot of:
     - Restaurant name, address, tax country
     - Order line items, quantities, and price snapshots
     - Tax rates (e.g. IVA 23%, 13%, 6%) and calculated tax amounts
     - Payment details, staff ID, and timestamp
   - The snapshot is permanently stored in `FiscalDocument.snapshot`.
   - Changes to menu item prices or restaurant settings never retroactively alter existing receipts.
3. **Cryptographic Integrity Hash**:
   - Each receipt generates a SHA-256 hash chaining document number, timestamp, totals, customer NIF, and the previous document's hash to guarantee tamper-evidence.
